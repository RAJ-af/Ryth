# Ryth: data and coding-model research plan

**Status:** research + proposed experiments, not results. Reviewed 2026-11-22. Goal: a reproducible, license-reviewed coding corpus and honest measurements for Ryth's scratch model. Hinglish mein: pehle data aur eval clean karo, phir training ko scale karo.

## 1. Evidence, not promises

These are findings from the cited authors, not measured Ryth improvements. Their models, datasets, and compute differ greatly from Ryth.

| Evidence | What it suggests; limitation |
|---|---|
| [The Stack](https://arxiv.org/abs/2211.15533) reports benefits from near-dedup on its Python experiments and describes governance and opt-outs. | Dedup is worth measuring, not proof that a particular Ryth threshold works. |
| [Deduplicating Training Data Makes Language Models Better](https://arxiv.org/abs/2107.06499) studies repeated substrings, memorization and train/test overlap. | File hashes alone miss copied snippets; similarity detection has false positives and negatives. |
| [StarCoder](https://arxiv.org/abs/2305.06161) describes multilingual pretraining followed by additional Python training; [StarCoder2/Stack v2](https://arxiv.org/abs/2402.19173) describes a broader data mixture. | Both use very large pretrained models/data. Neither validates the same recipe on Ryth 30M. Stack v2's dataset is gated; access and terms must be checked, not assumed. |
| [Textbooks Are All You Need](https://arxiv.org/abs/2306.11644) studies filtered and synthetic coding data and exercise fine-tuning. | Quality and format may matter; the paper's much larger model and teacher-generated data do not establish gains at Ryth scale or provide a reusable legal grant. |
| [FIM](https://arxiv.org/abs/2207.14255) reports infilling from a data transformation without harming left-to-right capability in its experiments. | Test both infilling and ordinary generation: no guarantee for Ryth's function-based FIM. |
| [Tokenizers Introduce Unfairness Between Languages](https://arxiv.org/abs/2305.15425) documents token-length disparity. [SentencePiece](https://arxiv.org/abs/1808.06226) describes a language-independent subword approach. | UTF-8 representability is not equal efficiency or quality; neither source proves a particular Ryth tokenizer mix. |
| [HumanEval/Codex](https://arxiv.org/abs/2107.03374) defines functional code evaluation; [MBPP](https://arxiv.org/abs/2108.07732) studies basic Python synthesis. [EvalPlus](https://openreview.net/forum?id=1qvx610Cu7) extends tests. | Passing a small test suite is imperfect evidence of correctness; benchmark version and execution settings matter. |
| [Self-Instruct](https://arxiv.org/abs/2212.10560) filters model-generated instructions for tuning; [Magicoder](https://arxiv.org/abs/2312.02120) uses open-source snippets to generate coding instructions. | Synthetic SFT is testable, not automatically correct, clean or license-free. Output-only imitation is not the soft-logit knowledge distillation in [Hinton et al.](https://arxiv.org/abs/1503.02531). |

**Scope distinction:** Scratch means initialize Ryth weights randomly and train on next-token/FIM data. Continued pretraining means start from an already pretrained *compatible Ryth checkpoint* and further train on code. SFT means tune a pretrained checkpoint on instruction/answer pairs. StarCoder, Codex and Magicoder findings are from pretrained-model regimes, not evidence that SFT can replace scratch pretraining. Importing an external pretrained checkpoint into Ryth is **not** an existing plug-and-play path; architecture, tokenizer, weights, runtime and license compatibility would need separate work. No external-score comparisons as if model sizes, prompts or data were matched.

## 2. Data contract before training (P0)

1. **Freeze source snapshot:** start with a small, reviewed set of original repositories in Python and C (matching Ryth's existing W2 PPL languages); add other programming languages only with explicit strata. Pin origin URL, immutable commit/revision, fetch date, path, file SHA-256, language, source version, transformation version and split. Keep raw and cleaned hashes. No credentials, personal data, vendored dependencies, build artifacts, generated bundles or notebook outputs; review secret-scanner misses on a sample. Public does not mean licensed.
2. **License policy:** store detected SPDX expression and evidence (repo LICENSE, relevant file headers, notices, path and revision), decisions, attribution/NOTICE obligations and reviewer. Reject unknown, conflicting, mixed or absent license until reviewed; preserve copyright/notice text in an attribution manifest. Do not treat a dataset card or source hint as proof of each file's rights. `corpus/licenses/spdx.py` puts MPL-2.0 in its `PERMISSIVE` set even though MPL has file-level copyleft obligations: remove it from a *proposed strict permissive experiment allowlist* until counsel reviews it; this document does not change implementation. SPDX license text: https://spdx.org/licenses/MPL-2.0.html ; SPDX identifiers: https://spdx.org/licenses/ . Training, redistribution, model release and generated-output obligations are separate legal questions; obtain legal review, not a claim of legal compliance.
3. **Provenance gaps:** `corpus/metadata/record.py` has repo/path/source/license/hash/split, but not full immutable revision, evidence, transformations, opt-out state or attribution chain. Add a versioned external manifest or implement those fields before a release. In `corpus/pipeline.py`, unknown detected license can fall back to `source.license_hint`; independently verify it rather than relying on the docs' stronger description. Keep dataset access agreements and teacher/provider terms with the manifest.
4. **Split and leakage:** cluster forks/repo families and exact/near-duplicate files **before** assigning entire clusters to train/dev/test. Freeze held-out source projects; keep validation and final test untouched by tokenizer training, FIM selection, synthetic seeds and teacher prompts. Existing `corpus/split/splitter.py` splits repo names, not fork families; `verify_no_leakage` only verifies repo names. Existing global file dedup drops copies, but does not ensure all related repos or snippets share a split. Implement external cluster mapping/split checks before calling the resulting holdout clean.
5. **Benchmark decontamination:** isolate HumanEval, MBPP and extended-test prompts, canonical solutions and tests from *all* training/teacher inputs; use case-preserving exact hashes plus normalized token/character-shingle and substring matching against entire source snapshots, docs and synthetic examples. Flag candidates, inspect common boilerplate, remove contaminated train records or quarantine affected eval tasks, and report counts/thresholds and both all-task and flagged-excluded scores. Matchers miss semantic/paraphrased leaks; report residual risk. Never train on benchmark tests as instructions.
6. **Removal path:** record duplicate-to-representative mappings and all originating repos/licenses, so a creator opt-out, privacy or rights complaint can find affected versions, shards, teacher-derived rows and checkpoints. Quarantine, rebuild affected dataset, document model/checkpoint remediation and acknowledge that removing a row cannot guarantee it is forgotten by already-trained weights.

Ryth building blocks: `corpus/cleaners/`, `corpus/licenses/`, `corpus/dedup/`, `corpus/quality/`, `corpus/pipeline.py`, `dataset/pipeline.py`, `dataset/lock.py`, `configs/w1_sources.json` and `scripts/w1_build_corpus.py`. `corpus/dedup/near.py` uses character shingles and approximate MinHash/LSH; measure recall against exhaustive exact-Jaccard pairs on a small stratified sample. `dataset/dedup.py` hashes packed chunks and is not a replacement for source-level or benchmark decontamination. `docs/corpus.md`, `docs/dataset_engine.md` and `docs/rds_format.md` describe current behavior, not legal guarantees.

## 3. Measurement protocol (common to all experiments)

- **Freeze** immutable data/benchmark versions, manifests and hashes, held-out repo families, tokenizer hash, architecture, context, prompts, stopping rules, decoding, tests, compute budget and seeds before comparing. Use training-only data for all tuning; choose on dev, run final held-out test once after selection. Create multiple disjoint train sets by family, not random chunks. Record post-filter token counts by language, source and license, unique repos, task counts, effective token exposures and repeats.
- **Baseline:** use the same initialized or pretrained checkpoint, data pool and hyperparameters as the intervention except the named factor. Report both matched token exposure/steps (isolates data quality) and retained unique data/repetition/coverage (reveals cost); if steps change, label an additional compute-budget comparison. Pair at least 3 training seeds where feasible, and bootstrap paired *problem-level* differences with 95% intervals; with tiny smoke sets report counts, not conclusions. Predeclare improvement as primary metric delta whose interval excludes zero, with no meaningful regression in the paired ordinary-code metric; otherwise inconclusive. No invented expected scores.
- **Completion:** `evals/humaneval.py`, `evals/mbpp.py`, `evals/metrics.py`; use frozen versions of HumanEval and MBPP (and HumanEval+/MBPP+ as stronger secondary tests). Primary: greedy pass@1, per-problem pass/fail and bootstrap interval; also syntax-valid rate, timeouts and output length. For sampled pass@k use same temperature/top-k/n and n >= k for every task; unbiased per-task estimator `1 - C(n-c,k)/C(n,k)`, average over problems. `evals/metrics.py` clamps k to n: explicitly reject/report invalid n < k externally rather than treating it as pass@k. Record samples and exact tests. Base completion prompts and SFT chat prompts must be specified separately; compare within each prompt protocol and report both if comparing regimes.
- **Held-out LM:** `evals/ppl.py` / `ryth-eval ppl` on independently sourced repo-family holdouts, separately by programming language. Compare PPL only with the same tokenizer and identical text/boundaries; across tokenizers use total negative log likelihood per UTF-8 byte (bits/byte = total NLL in nats / (ln(2) × bytes)) with the same normalization, BOS/EOS treatment and scored text. Also report total tokens and context truncations. Hindi/Hinglish/English are natural languages; Python/C/etc. are programming languages: measure each independently, plus mixed code-and-comment examples.
- **Safety:** `evals/execution.py` and SFT test generation execute arbitrary generated code in a local subprocess with a timeout, **not a security sandbox**. Generate separately; execute only in a disposable isolated VM or hardened sandbox, no network/secrets/host mounts, unprivileged, read-only filesystem except bounded scratch, CPU/memory/process/output/time limits. Review container escape risk; a default container alone is not a complete security boundary. [HumanEval's official harness](https://github.com/openai/human-eval) warns the same; [BigCode's harness](https://github.com/bigcode-project/bigcode-evaluation-harness) documents additional multilingual and FIM tasks.
- **Existing Ryth smoke is not quality evidence:** `docs/w2_baselines.md` / `results/w2_humaneval_baseline.json` and `results/w2_mbpp_baseline.json` report random weights, 40 tasks, one sample, 32 new tokens, not a trained baseline. Its provisional Python PPL input was derived from HumanEval; never use it as clean held-out PPL. Obtain a compatible trained checkpoint and independent holdout before claiming improvement. The same docs' speculative expectations are not measurements.

## 4. Prioritized controlled experiments

Numbers below are **design choices**, not reported results. First make P0 gates above pass. Every trainable arm uses the protocol in §3; do not run all expensive grids at once.

### P1 — quality filtering and dedup (scratch or continued pretraining)

**Hypothesis:** modest cleaning/dedup improves generalization per training token without excluding useful low-resource code. After mandatory legal/security/decontamination gates, compare (A) minimal hygiene + exact dedup and no quality threshold; (B) A + near-dedup; (C) B + repo-quality threshold 40 (`corpus/config.py` current default). For a clean quality-only comparison add (D) A + threshold 40. Same eligible source snapshot and same fixed split assignment; train equal token exposures, record repeats, and run a same-unique-data secondary comparison when feasible. Dedup and split processing need an external cluster map; do not accidentally change holdout composition across arms.

Review 100 stratified accepted and 100 rejected items per intervention if available, stratified by language/repo/size, for useful code, parse validity, generated/vendor and secret misses; record reviewer disagreement and false-drop examples. Report retained bytes/repos/tokens, duplication estimates, Python and C bits/byte/PPL, HumanEval/MBPP pass@1, and cost. Run a small labeled duplicate-pair audit including forks, renamed/whitespace variants, partial-copy snippets and unrelated boilerplate; compare approximate detector recall/precision to manually checked ground truth. **Go:** primary held-out code loss improves with non-regressing completion and acceptable retention across strata. If quality filter removes a language disproportionately, adjust only on dev and rerun. Implementation: `corpus/quality/`, `corpus/dedup/`, `corpus/report.py`, `dataset/quality.py` and `training/`; stratified labels and cluster checks are new work.

### P2 — multilingual tokenizer allocation (scratch branch only)

**Hypothesis:** a balanced code + English/Hindi/Hinglish tokenizer reduces token inflation for underrepresented scripts without damaging code efficiency. Freeze disjoint held-out texts; train two equal-vocabulary byte-BPEs via `tokenizer/train.py` / `tokenizer/bpe.py`: A existing code-heavy train mix, B controlled mixed-language train mix (e.g. equal sampled UTF-8 bytes from code, English, Hindi and Hinglish; log actual input bytes and tokenized exposure). Freeze same special-token set and vocabulary budget, respecting RDS `uint16` limit. Check NFC-normalized round-trip, source-code syntax/semantic preservation, whitespace and special-token collisions. NFC can change source bytes or identifiers/string literals, so test and quarantine cases rather than silently assuming exact original-byte preservation.

Measure held-out tokens/UTF-8 byte and tokens/character by script and programming language, context-window truncation, and encode throughput (`scripts/tokenizer_report.py`, `scripts/w1_tokenizer_efficiency.py`, `scripts/bench_tokenizer.py`). If worthwhile, train two scratch models at matched parameter and compute budget; compare bits/byte and task performance, not cross-tokenizer PPL. Training a tokenizer from train data is cheap relative to two model trainings, but building a new vocabulary changes embedding/LM-head interpretation: existing Ryth weights cannot simply be used with new IDs. `extend` preserves old IDs but new embeddings/head rows and checkpoint compatibility need explicit implementation/training and tests. **Go:** reduced disparity without material regressions in code tasks or loss; publish per-stratum deltas.

### P3 — fill-in-the-middle (scratch or compatible continued pretraining)

**Hypothesis:** FIM improves code insertion without materially degrading ordinary completion. At matched token exposures, compare FIM rates 0%, 15%, 50%, retaining next-token examples for the remainder. Pre-register whether rate means fraction of eligible examples or tokens; log both, middle-span distribution, selected functions, actual sentinels and packed boundaries. `dataset/fim.py` uses function-oriented PSM form; this is not necessarily the random document-span distribution in the FIM paper. `corpus/tasks/` has a separate FIM path: select one, don't apply both. Verify the registered tokenizer IDs and exact PSM order; test prefix + generated middle + suffix reconstruction.

Build a held-out repo-family insertion set with spans excluded from training and record prompt length, language and span length; evaluate exact match **and** parse/compile/test pass on reconstructed files. Baseline is same checkpoint/seed with FIM disabled; secondary left-to-right metrics are §3 code loss and HumanEval/MBPP. SantaCoder-FIM in the [BigCode harness](https://github.com/bigcode-project/bigcode-evaluation-harness) is an additional benchmark but needs a Ryth adapter and matching sentinel convention, not an existing Ryth CLI. **Go:** FIM improves functional insertion with no meaningful loss on ordinary generation; verify the two outcomes jointly.

### P4 — instruction tuning / teacher-output imitation (requires pretrained Ryth)

**Hypothesis:** execution-checked instruction pairs improve held-out coding instruction compliance versus base and unfiltered synthetic SFT. Starting from the *same pretrained compatible checkpoint*, compare (A) base/no SFT, (B) SFT on rule-filtered teacher pairs, (C) same-sized SFT on independently test-checked pairs from the same teacher/seed pool. Match task mix, input/output tokens, optimization steps, chat template, model and budget; repeated sampling and verification calls count toward cost. A/B/C are output imitation, not logit distillation. Genuine soft-target distillation requires teacher logits, compatible token distributions/alignment and a separate KL-loss implementation; do not call an API answer-only dataset logit distillation.

Only use train-family snippets with approved source/teacher rights, no secrets or benchmark material. Freeze teacher model/version, prompt, sampling, provider terms, costs, source IDs, generation/test results and rejection reasons. Human-review a stratified sample for correctness, safety, attribution and prompt diversity. Test-generated assertions alone are weak/self-confirming: use independent hidden tests where possible and report syntax pass, execution pass, held-out prompt-family functional pass@1, instruction-following and human error rate. Teacher self-review is not independent proof. Reject contamination and near-duplicate prompts/responses. Hold out **entire seed repo and prompt families before packing**: `sft/build.py` currently shuffles packed chunks for validation, so one conversation or family may cross splits; separate build inputs and implement/verify split-aware packing before trusting val scores. Use `sft/filter.py`, `sft/generate.py`, `sft/teacher.py`, `sft/build.py`, `sft/train.py`; assistant-only masks are implemented, but independent tests, family splits, task-specific evaluation and rights audit are additional work. **Go:** C beats B and A on held-out instruction tasks with no meaningful ordinary-code regression; otherwise retain base or simpler SFT.

## 5. Budget, feasibility and sequence

1. **P0, CPU first:** source/rights inventory, split clusters, decontamination, safe execution and 200-item filter audit. Effort dominated by human review and pair matching; approximate dedup can be CPU/RAM heavy. For a pilot cap source volume and time every stage before scaling; keep false-negative audits.
2. **P1 small pilot:** use `ryth_30m` and one seed per arm to screen, then 3 seeds for promising arms. Example budget per arm: 2,000 steps × 8 microbatch × 4 accumulation × 1,024 context = **65,536,000 token slots** on one device (padding and repeats are not unique tokens); defaults in `training/config.py`, not a measured throughput. Four arms × three seeds = 786,432,000 slots, plus evaluation and failed runs. Record actual non-pad tokens and peak GPU memory. Measure a 100-step warm run on target hardware: estimated training GPU-hours = total remaining steps / measured steps per second / 3,600, plus checkpoint/eval overhead; stop if quota is insufficient.
3. **P2 CPU-only token audit**, then two scratch trainings only if tokenizer gap merits the cost; tokenizer change forces full re-encoding and fresh model weights. **P3** uses three FIM arms; first screen and promote rather than running three seeds blindly. RDS stores uint16 token IDs: 65.536M unpadded tokens are roughly 131 MB decimal raw token payload, excluding shard headers, masks, raw corpus, duplicates, validation and checkpoints. Disk and network needs depend on actual source size.
4. **P4** only after a pretrained checkpoint and safe evaluator exist. Pilot e.g. 500 teacher candidates, set an API dollar and output-token cap before calls, record all attempts and human/test costs. Provider price and accepted yield are unknown: projected cost = input tokens × input price + output tokens × output price + verification calls, plus human review and training. Hosted APIs may forbid certain reuse or transfer of source; check before sending. Existing `docs/sft.md` notes real generation requires credentials.

For every run save git commit, data/split/tokenizer/benchmark hashes, config, model initialization/checkpoint hash, seed, hardware, wall-clock, measured tokens/s, GPU-hours, peak RAM/VRAM, disk, API spend, all evaluation generations/results and caveats. No run has been executed for this plan. A missed gate or inconclusive interval is a result, not permission to claim an improvement.
