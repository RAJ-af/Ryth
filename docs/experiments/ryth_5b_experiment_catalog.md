# Ryth 5B experiment catalog and safety roadmap

**Status: proposed research, not results or an approved 5B training plan.** Priorities are sequencing, not expected gains. Begin with a reproducible trained small-model baseline; promote only measured winners. A **5B scratch run** learns the base model from random initialization, whereas **fine-tuning** adapts an already pretrained checkpoint. Inference-only retrieval/quantization do neither. No 5B experiment below has been run.

Companion plans: [efficient pretraining research](efficient_pretraining_research.md) and [data and coding research](data_and_coding_research.md). Existing guides: [training](../training.md), [model](../model.md), [evals](../evals.md), [W2 baselines](../w2_baselines.md), [kNN design](knn_memory_head.md), [W1 runbook](../w1_runbook.md).

## Evidence and implementation constraints

- [W2](../w2_baselines.md) records a **random-initialized** 24.3M, near-byte vocab 260, seed 1234, length 256 CPU model: HumanEval and MBPP pass@1 0/40 each, Python PPL 212.51 ([PPL JSON](../../results/w2_ppl_baseline.json), [HumanEval](../../results/w2_humaneval_baseline.json), [MBPP](../../results/w2_mbpp_baseline.json)). The PPL source is provisional HumanEval-derived text; never use it as an independent coding-quality holdout. These are harness checks, not trained-quality or 5B baselines.
- The [Kaggle smoke report](../../results/RYTH_Kaggle_Smoke_Test_Report.md) reports 12 FP16 T4 steps, 24.4M params, vocab 482 and PPL 79.11 on a tiny corpus. It demonstrates plumbing, not generalization; its PPL is not comparable to W2 due to tokenizer/data differences.
- [RythConfig](../../model/config.py) has dense GQA/SwiGLU presets through `ryth_1b`, **no 5B preset**; its estimate depends on vocabulary and tying. [SwiGLU](../../model/feedforward.py) is dense; MLA is a stub. There is no implemented MoE, distillation, growth, LoRA or quantization path identified in the Python code. A custom 5B config needs measured parameter count, checkpoint compatibility and infrastructure review; this is not simply a preset switch.
- [TrainConfig](../../training/config.py) defaults to AdamW, cosine, 1,024-token sequences and bf16. [RDE defaults](../../configs/rde_default.json) instead specify length 4,096, vocab 32,768 and FIM rate 0.5: explicitly align tokenizer, context, packing, masks and objective for every arm. [Dataloader](../../training/dataloader.py) falls back to a random **chunk** holdout when no separate validation directory is supplied; this is not repository-disjoint. Use separately built, deduplicated repository-disjoint splits instead. Source license hints in [W1 config](../../configs/w1_sources.json) are not verified licenses.
- Existing [model tests](../../tests/test_model.py) exercise causality, cache equivalence and checkpoints; [training tests](../../tests/test_training.py) cover loss, NaNs and resume; [SFT tests](../../tests/test_sft_build_train.py) cover masks. Extend these for each new mechanism, not as evidence of 5B scalability. [SFT loader](../../sft/train.py) reconstructs a named preset; custom 5B checkpoints need a compatible config/loader before SFT.

## Common protocol and decision rules

1. **Freeze data first.** Record source/revision, license/consent and redistribution restrictions, repository-level split assignment, exact and near-duplicate checks across all splits and benchmark prompts/solutions, secret/PII scans and takedown procedure. Quarantine unknown rights or contamination. Keep train, tuning and sealed test independent, including retrieval indexes, teacher data and quantization calibration. Record manifests and hashes; do not treat a license hint as permission.
2. **Baseline B0 (P0, required):** train dense 30M on real permitted data, then 125M if feasible, with separate held-out Python/C and a frozen tokenizer and context. Fix architecture, initialization, objective/FIM mixture, effective batch, data order, precision, optimizer, schedule, and total non-padding predicted tokens. Use paired seeds (at least 3 for training comparisons where affordable). Save git SHA, full configs, tokenizer/dataset/split hashes, checkpoint/optimizer/RNG, hardware and software, step/token counts. Confirm resume reproducibility and no nonfinite loss. Run [training benchmark](../training.md#benchmark), [W2 post-training eval commands](../w2_baselines.md#post-training-rerun-30m-checkpoint-full-settings), and existing tests. B0 is planned; 40-task random scores are not its control.
3. **Evaluation:** primary is token-weighted held-out negative log-likelihood (NLL) and PPL `exp(NLL)` per language and aggregate; compare PPL only with identical tokenizer, corpus and context. Report HumanEval/MBPP pass@1 and task-level outcomes with fixed prompts, decoding, sample count and seeds; report uncertainty (paired bootstrap over held-out repositories for NLL and tasks for pass@1, plus between-seed variation). Tune only on tuning data, freeze selection before one sealed-test evaluation. Do not use the HumanEval-derived provisional text for this comparison. Failure to get independent data or meaningful uncertainty = inconclusive, not a win.
4. **Cost accounting:** record GPU type/count, allocated GPU-hours including failed trials, teacher/index/calibration and evaluation costs, wall time, peak allocated and reserved VRAM, CPU RAM, disk, total/active parameters, measured tokens/s, and p50/p95 prefill and per-token decode latency at fixed batch/context. Include amortization assumptions and throughput warmup. For training techniques report both equal-data/tokens and equal total compute or GPU-hour comparisons; if hardware differs, report FLOPs and price assumptions separately. Never infer measured speed from parameter counts.
5. **Pre-register promotion gates:** proposed default for training experiments: paired mean NLL no worse than control by 0.01 nats/token on sealed test, no language worsens by more than 0.02, and either NLL improves by at least 0.01 with a paired 95% CI excluding zero, or measured total GPU-hours/peak VRAM falls at least 15% with NLL non-inferiority supported by the paired 95% CI. Report pass@1 changes with uncertainty; a statistically credible regression or any critical safety failure blocks promotion. Thresholds are decision tolerances, not predictions; pre-register task-specific tolerances and multiplicity for sweeps. An uncertainty interval spanning the gate is inconclusive. Always publish negative/inconclusive results and all trials.

## Prioritized registry

All entries are **planned**, require B0 and the common protocol, and are not implemented unless explicitly noted. Relative cost categories refer to B0 on the same device; actual budgets must be approved after measured pilot throughput.

### R5-01 — kNN memory head (P1; inference only)

- **Hypothesis/source:** interpolation with a datastore of pretrained hidden states can lower NLL on held-out code without updating weights ([kNN-LM](https://arxiv.org/abs/1911.00172)). This is the existing [design-only Ryth experiment](knn_memory_head.md), gated on a trained W1 checkpoint; it is not implemented or a 5B scratch training method.
- **Control/protocol:** same frozen checkpoint, tokenizer, decoding and evaluation, with λ=0. Build train-only index from permitted, deduplicated RDS; key is final normalized hidden at t, value is token t+1; skip last positions. Hash index/checkpoint/data, test alignment and exact neighbor lookup, assert no tuning/test documents or near duplicates. Select `k`, temperature and λ on tuning only; use a smaller preregistered subset of the design's grid and freeze before test. Compare rare-token and language slices; random weights or shuffled values are diagnostic controls, not proof that improvement is impossible.
- **Success/failure:** primary paired NLL improvement ≥0.01 nats/token, 95% CI excluding zero, plus no critical safety or per-language regression under common gates; otherwise fail/inconclusive. Report pass@1, latency, index coverage and leakage checks even if NLL improves. A gain with excessive latency is not a deployment win.
- **Cost:** one train-corpus forward pass and storage plus every query's search; no retraining. At d=512, fp16 key + int32 token costs 1,028 bytes/entry: 2M ≈2.06 GB, 5M ≈5.14 GB decimal before metadata/index overhead. At 5B use its actual d; flat search scales with entries × d and may dominate decoding. PCA/ANN are separate ablations with quality and recall costs. Retrieval may expose licensed text, secrets or verbatim code; audit outputs and govern deletion/index rebuild.

### R5-02 — low-rank optimizer state for scratch (P1)

- **Hypothesis/source:** [GaLore](https://arxiv.org/abs/2403.03507) projects gradients for optimizer state while allowing full-parameter learning; unlike LoRA, it is a candidate for scratch pretraining. The authors report a 7B scratch-training feasibility demonstration on a 24 GB GPU with their specialized setup and small token batch; this establishes neither fast training nor a Ryth result. Paper results on other models/data do not guarantee a Ryth saving.
- **Control/protocol:** dense AdamW B0 versus same dense model/data with a newly implemented compatible low-rank optimizer, preregister rank/projection update interval and which matrices are projected; keep norms/embeddings and excluded parameters explicit. Test gradients, optimizer-state save/resume and tied weights. Run equal-token and equal-total-GPU-hour comparisons at 30M then 125M.
- **Success/failure:** common NLL/non-inferiority and ≥15% measured peak VRAM or GPU-hour savings gate; track divergence, gradient norms, projection overhead and per-language NLL. Fail on NaNs, resume mismatch or no statistically supported quality/cost tradeoff.
- **Cost:** two or more training runs plus projection/SVD overhead and tuning; low-rank optimizer states do not remove weights, activations or checkpoint overhead. New dependency/kernel behavior and hardware support need audit.

### R5-03 — post-training quantization (P1; inference only)

- **Hypothesis/source:** [GPTQ](https://arxiv.org/abs/2210.17323) suggests weight-only quantization of a trained model; it does not prove cheaper 5B scratch training. Calibration and actual kernels matter.
- **Control/protocol:** same trained dense checkpoint in supported FP16/BF16 versus int8 then 4-bit weight-only candidates. Calibrate only on permitted training data, not tuning/test. Preserve or explicitly test tied embedding/head behavior; implement compatible loading, cache and generation tests. Benchmark fixed hardware/batch/context and end-to-end decoding, including conversion and metadata.
- **Success/failure:** paired NLL non-inferiority ≤0.01 nats/token with 95% CI, no critical safety/pass@1 regression, and ≥15% measured model footprint or peak inference VRAM reduction. Report p50/p95 latency and throughput; fail deployment-speed claim if no measured end-to-end gain. Regression or unsupported kernels stops promotion.
- **Cost:** calibration forward passes, conversion, checkpoint copies and eval; nominal 5B weights alone are ~10 GB at 16-bit or ~2.5 GB at 4-bit, decimal, excluding scales, unquantized tensors, KV cache, workspace and runtime overhead. These are storage arithmetic, not fit or speed guarantees.

### R5-04 — LoRA/QLoRA adaptation (P2; fine-tuning only)

- **Hypothesis/source:** [LoRA](https://arxiv.org/abs/2106.09685) freezes pretrained weights and trains low-rank updates; [QLoRA](https://arxiv.org/abs/2305.14314) adds a quantized frozen base. Neither substitutes for pretraining a 5B model from scratch.
- **Control/protocol:** after a compatible pretrained checkpoint exists, compare full SFT ([sft/train.py](../../sft/train.py)) versus LoRA on the same instruction split, masks, tokens, steps, scheduler and prompts; add QLoRA only after quantized loader/kernel checks. Pre-register target modules, ranks and scale, adapter merge and tied-weight policy. Verify frozen parameters, gradients, mask behavior and save/reload parity. Teacher-generated SFT data requires source/teacher rights and filtering.
- **Success/failure:** use common quality/cost gates on assistant-token validation NLL, fixed coding eval and general base PPL to detect forgetting; ≥15% lower peak training VRAM or GPU-hours with non-inferiority is a candidate, not assumed. Reject unstable training or adapter regression; safety regressions block release.
- **Cost:** full SFT plus adapter runs and, for QLoRA, quantization/conversion overhead; base weights and activation memory remain. Custom 5B SFT loading and adapter implementation are prerequisites.

### R5-05 — distillation (P2; scratch student or adaptation, not free compute)

- **Hypothesis/source:** teacher soft targets can transfer predictive information to a student ([Hinton et al.](https://arxiv.org/abs/1503.02531)); paper results do not establish a Ryth or 5B gain. A random-init 5B student distilled during pretraining is still a scratch student but depends on an existing trained teacher; distilling an existing checkpoint is adaptation.
- **Control/protocol:** first 30M scratch student: ordinary next-token cross-entropy versus fixed teacher logits + hard-token loss, same student, tokens, data and schedule; define temperature/weight before test. Use a teacher with compatible tokenizer/vocabulary or implement and validate explicit alignment; never silently compare mismatched token logits. Same training-only inputs for teacher and student; record model/license, teacher token overlap and whether logits are cached. For equal-compute control include teacher inference and cache generation, then compare an ordinary student trained for the same total budget.
- **Success/failure:** common paired NLL/cost gate and coding pass@1; test memorization, teacher contamination and quality on each language. Fail if teacher rights/alignment are unclear, leakage occurs, or gain disappears after full teacher costs.
- **Cost:** teacher forward compute, storage/I/O for logits and student training; no teacher is assumed available. Generated text or logits may inherit license, safety and privacy restrictions.

### R5-06 — progressive depth growth (P2; scratch pretraining)

- **Hypothesis/source:** start shallower and grow depth to reduce early-stage compute; [Progressively Stacking 2.0](https://arxiv.org/abs/2011.13635) studies BERT layerwise growth/freezing, not this causal decoder. [Stacking Your Transformers](https://arxiv.org/abs/2405.15319) studies model growth in LLM pretraining. Neither paper's speedup can be transferred directly to Ryth. Our first test is depth growth with all layers trainable after each growth event, not a claim to reproduce either paper.
- **Control/protocol:** dense fixed-depth B0 versus identical final depth, width, tokenizer and data, with a fixed two-stage schedule (e.g. half depth for first 25% of tokens, full depth thereafter). Define new layer initialization, optimizer-state migration, LR/scheduler continuity and checkpoint metadata; test causal/cache parity and deterministic resume across growth. Compare equal data/tokens and equal total GPU-hours, including earlier stages and migration; retain random-init final-depth control.
- **Success/failure:** common NLL and ≥15% measured compute/VRAM gate; also measure loss spikes and recovery immediately after growth. Fail on divergence, final quality regression or no net saving. Do not call a shallower intermediate model a finished 5B model.
- **Cost:** multiple complete runs plus engineering and stage-transition tests; new state/versioning and extra tuning can erase savings.

### R5-07 — sparse MoE feed-forward (P3; scratch architecture)

- **Hypothesis/source:** [Switch Transformer](https://arxiv.org/abs/2101.03961) uses sparse expert routing; sparse active parameters are not the same as total parameter count, and paper results on T5 do not predict Ryth performance.
- **Control/protocol:** implement a small top-1 routed SwiGLU experiment with explicit capacity, overflow/drop policy, auxiliary load-balancing loss and deterministic routing. Compare dense baseline at matched training tokens and measured total compute/GPU-hours, then separately at matched total parameters; log total and active parameters, routing counts per expert/language, dropped tokens and communication. Unit-test routing, masks, gradients, cache, checkpoint/resume and single-device parity before distributed work.
- **Success/failure:** common NLL/non-inferiority and cost gate plus no unbounded drops, collapsed experts, routing instability or language-specific degradation. Include imbalance and worst-slice results; reject an apparent compute win that omits routing/communication or higher inference memory.
- **Cost:** expensive new implementation, expert storage, dispatch and potential all-to-all communication; matched-token and matched-compute controls require multiple full runs. Only consider a 5B-total vs 5B-active definition after smaller pilots establish feasibility.

## Safety and scale-up gates

1. **Before any run:** approve data/teacher licenses and provenance, contamination/secret scans, independent split manifest, budget and kill switch. Do not expose sensitive training text in logs, retrieval stores or model outputs. Review supply-chain dependencies and limit checkpoint access; load only trusted checkpoints (existing SFT uses `torch.load(..., weights_only=False)`).
2. **Before executing generated code:** the current [execution harness](../../evals/execution.py) uses a local subprocess and timeout, **not a security sandbox**. Run only in a disposable, isolated environment with no network or credentials, unprivileged user, read-only inputs, strict CPU/memory/process/time/output limits and teardown; validate isolation independently. A container alone is not a guarantee. Never execute untrusted samples on a host with secrets.
3. **Before promotion:** require clean tests and resume, finite-loss monitoring, sealed evaluation, slice and uncertainty reports, PII/secret and verbatim-extraction probes, harmful/insecure code review, source/takedown process and known limitations. Test safety and license behavior separately from capability; PPL/pass@1 do not establish safety. Stop, quarantine artifacts and investigate on leakage, loss instability, compromised isolation, budget overrun or material safety regression.
4. **Before 5B scratch authorization:** select an explicit config and count unique tied parameters, demonstrate hardware fit including optimizer/activations/checkpoints and failure recovery, estimate training tokens and cost from measured smaller runs, secure sufficient clean data, then approve a capped pilot and go/no-go review. A nominal parameter target does not establish data or compute sufficiency. [Compute-optimal scaling](https://arxiv.org/abs/2203.15556) motivates jointly budgeting model and data, not treating its ratios as a guaranteed rule for Ryth code. Fine-tuning or inference experiments on an external 5B checkpoint require separate rights, compatibility and evaluation; they do not demonstrate a scratch 5B capability.

Primary-paper metadata was checked against public sources. All cited paper findings concern their own experimental settings; none are asserted as measured Ryth gains.
